# 小红书图文策略

本文件只定义小红书视觉资产和图文结构的工作策略，不包含发布、登录、Cookie、定时发布和数据运营。

## 目标

小红书图文要同时解决三个问题：

1. 缩略图状态下能否快速识别主题
2. 用户是否能看出点击理由
3. 连续翻页后是否能得到具体信息

封面负责点击理由，内页负责内容推进，文案元数据负责补充标题、正文、标签和互动问题。三者使用同一内容主张，避免封面承诺与正文脱节。

## 默认规格

| 资产 | 默认比例 | 推荐尺寸 | 说明 |
|---|---|---|---|
| 封面 | 3:4 | 1080x1440 | 竖幅主视觉，强调缩略图识别 |
| 轮播卡片 | 3:4 | 1080x1440 | 逐页承载一个主要信息任务 |
| 方形卡片 | 1:1 | 1080x1080 | 用户明确需要时使用 |
| 机制图或横向对比图 | 16:9 | 按任务确定 | 只有内容需要横向空间时使用 |

如果用户给出明确尺寸或比例，用户要求优先。每项资产都必须在需求契约、计划、提示词元数据和实际检查中保持一致。

## 封面锚点

每张小红书封面必须建立以下字段：

```text
click_hook: 用户为什么要点开
visual_anchor: 缩略图中最先被看到的主体
trust_signal: 数字、界面、结果、证据或具体场景
safe_crop_zone: 标题和主体的安全区域
thumbnail_readability: 缩小后仍需辨认的元素
```

优先选择以下内容作为点击钩子：

1. 具体结果或前后变化
2. 数字、时间、成本或效率差异
3. 读者熟悉但尚未解决的冲突
4. 真实界面、操作步骤或产品证据
5. 具有方向性的观点
6. 一个可观察的动作或场景

避免使用没有内容支撑的“必看”“震撼”“保姆级”等空泛承诺。

## 封面风格选择与咨询

用户提供文章但没有指定视觉方向时，先提取内容类型、核心主张、点击钩子、主要证据、视觉主体、标题长度、情绪和可用素材，再从 `style-library.md` 选择三个明显不同的封面方向。每个方向必须同时写出主风格、封面结构、冲击机制和与文章直接相关的理由。推荐项放在第一位，只进行一次选择确认。

用户已经指定风格、提供完整提示词、要求跟随参考图，或明确说“自动决定”“直接出图”时，不再询问。用户只选择封面方向，内页自动继承封面的主色、字体行为、材质、线条和图形语言。

选择时优先判断文章最需要放大的传播信号：

1. 有真实结果或状态变化时，优先考虑结果冲突或前后对照。
2. 有关键数字时，优先考虑数字证据。
3. 有真实产品界面和操作路径时，优先考虑界面证据、产品主视觉或触觉界面拼贴。
4. 有作者经历、人物动作或具体物件时，优先考虑人物与行动。
5. 有强观点、行业判断或抽象关系时，优先考虑概念张力或高级概念海报。
6. 有教程、方法和工作流时，封面只压缩一个最值得点击的结果或冲突，完整步骤留给内页。

## 封面生成路线

每项资产在 `requirements.json` 和 `plan.md` 中记录 `render_method`，允许值为 `imagegen` 或 `html`。

小红书封面在没有特殊渲染要求时默认使用 `imagegen`，优先把人物行动、产品场景、概念隐喻、强透视、空间纵深、图文穿插、拼贴、纸雕、摄影或电影化光线交给 AI 生图表达。直接生成中文标题时，视觉短标题优先控制在四至八个汉字，只保留一级主标题和确有必要的少量辅助文字。

完整长标题必须逐字准确，或数字、表格、参数、流程、多级文字、真实截图标注、严格品牌版式或精确布局承担主要信息时，优先使用 `html`。用户指定生成方式时，以用户选择为准。

教程型图文包默认采用混合路线：封面按上述规则选择生成方式，信息密集内页使用 HTML 或 React，再统一导出到 `images/` 并进入整体交付预览页。

## 页面节奏

知识型内容推荐使用五至八页：

```text
封面钩子
→ 问题确认
→ 核心观点
→ 机制或步骤
→ 案例或证据
→ 边界与风险
→ 行动建议
→ 互动问题
```

短内容可以合并页面，长内容可以拆开证据和步骤。每页必须提供：

```text
page_role
information_answer
exact_text
visual_anchor
evidence
safe_crop_zone
```

## 内容类型路由

| 内容类型 | 主要视觉资产 | 第一优先级 |
|---|---|---|
| 工具教程 | 界面证据、步骤卡片、机制图 | 输入、动作和结果 |
| 技术解释 | 模块关系、流程图、结构化卡片 | 机制和边界 |
| 观点文章 | 概念海报、冲突对照、隐喻场景 | 立场和张力 |
| 产品体验 | 使用场景、前后对比、结果证据 | 具体收益和适用条件 |
| 个人经历 | 人物叙事、时间线、物件证据 | 真实细节和转折 |

不要给每一段文字机械配一张图。只有当视觉能补充结构、证据、关系、对比或记忆点时，才安排独立页面。

## 叙述视角

当来源是用户本人或原作者的经历、教程、测评和复盘时，默认使用 `author-first-person`：

1. 发布正文直接写“我怎么做、我看到什么、我如何判断”。
2. 图片内解释文字写实际操作和结果，例如“我上传原始数据”“我让结果进入知识库”。
3. 避免“文章里说到”“原文提到”“作者发现”“文中展示”等转述话术。
4. 只把来源中明确发生的动作写成亲历，禁止把推测、外部事实或未验证结果改写为个人体验。

第三方新闻、研究、他人案例和引用资料继续保留必要归因，使用 `attributed-source`。把最终选择写入 `requirements.json` 的 `narrative_voice`。

## 资料图片与截图

资料中的截图、照片、图表和界面图片属于内容证据。先建立素材清单，再决定页面结构：

1. 记录素材顺序、相邻解释文字、原始尺寸、主题、用途和目标页面。
2. 教程截图与对应步骤说明优先放在同一张卡片中，避免读者跨页猜测截图含义。
3. 截图保持原始比例和事实内容，可以裁去无关空白、放大重点或使用总览加局部的组合。
4. 标题、编号、箭头、框选和解释文字使用独立排版层，不能覆盖关键界面、修改数据或重绘产品界面。
5. 一张截图缩小后无法阅读时，拆页或单独放大，不用极小字号和过度压缩维持页数。
6. 多张截图表达连续步骤时，按操作顺序编号，并让每张截图紧邻自己的解释。

## 文案元数据

可以输出以下字段，作为发布前素材：

```text
title
body
tags
comment_cta
narrative_voice
```

标题长度、正文长度和标签数量使用可配置工作预设。当前文件不把这些预设描述为永久官方限制，也不负责实际发布。
